# 05 知识库与文档流水线 knowledge

路径：`backend/src/main/java/com/group4/kaoyan/modules/knowledge/`

```
modules/knowledge/
├── controller/KnowledgeController.java     /api/kb/*、/api/doc/*
├── service/KnowledgeService.java           知识库与文档 CRUD（权限门都在这里）
├── service/DocumentProcessService.java     异步流水线：解析 → 切片 → 向量化
```

数据流分两条：**写入侧**（上传 → 流水线 → Milvus）、**读取侧**（问题 → 检索 → 上下文）。
两条都在本模块，只有最终组 Prompt 和流式生成在 `chat` 模块。

### 2) 状态机

```
UPLOADED → PARSING → SPLITTING → EMBEDDING → READY
                                   ↘ FAILED（写入 error_msg）
```

路径：`backend/src/main/java/com/group4/kaoyan/modules/knowledge/service/DocumentProcessService.java`

```java
@Async("documentExecutor")
public void process(Long docId) {
    try {
        updateStatus(docId, "PARSING", null);
        String text = parserFactory.parse(storageService.download(doc.getObjectKey()), doc.getFileExt());
        if (text == null || text.isBlank()) throw new BizException("未解析出文本内容，扫描件请先做 OCR");

        // 全文落库 + 哈希（保留原文，重解析不用回 MinIO 下载两次）
        meta.setRawText(text);
        meta.setContentHash(DigestUtil.md5Hex(text));

        updateStatus(docId, "SPLITTING", null);
        List<String> pieces = textSplitter.split(text);
        chunkMapper.deleteByDocId(docId);                    // 先清旧切片，保证可重复执行
        for (int i = 0; i < pieces.size(); i++) {
            KbDocumentChunk c = new KbDocumentChunk();
            c.setChunkIndex(i); c.setContent(pieces.get(i)); c.setCharCount(pieces.get(i).length());
            chunkMapper.insert(c);
            c.setMilvusId(c.getId());                        // Milvus 主键 = 切片 id
            chunkMapper.updateById(c);
        }

        updateStatus(docId, "EMBEDDING", null);
        embedAndIndex(docId, doc, chunks);                   // 按 EMBEDDING_BATCH_SIZE 切批

        ok.setChunkCount(chunks.size());
        ok.setStatus("READY");
    } catch (Exception e) {
        updateStatus(docId, "FAILED", brief(e.getMessage())); // 失败不抛出，只落状态
    }
}
```

几个容易踩的点：

- `parserFactory.parse` 拿不到文本（扫描版 PDF 没有文本层）→ 直接 `FAILED`，需要另外接 OCR；
- `chunkMapper.deleteByDocId` 先删再插，所以 `reparse` / `reindex` 可以安全重跑；
- `contentHash` 算了但**没有做去重**，同一份文件重复上传仍会重复切片、重复占用向量；
- 失败只写 `FAILED + error_msg`，不抛异常——异步线程里抛出去没人接。

```java
int size = Math.max(100, props.getRag().getChunkSize());            // 默认 400
int overlap = Math.max(0, Math.min(props.getRag().getChunkOverlap(), size - 1));  // 默认 80
while (start < text.length()) {
    int end = Math.min(text.length(), start + size);
    if (end < text.length()) {
        int cut = text.lastIndexOf('\n', end);                      // 优先在换行处截断
        if (cut > start + size / 2) end = cut;
    }
    ...
    start = Math.max(start + 1, end - overlap);                     // 保留 overlap 重叠
}
```

切片前会做 `\r\n → \n`、连续空行压缩成两个换行，避免 PDF 里那种满屏空行把窗口吃掉。

## 二、读取侧：检索

路径：`backend/src/main/java/com/group4/kaoyan/modules/knowledge/service/RetrievalService.java`

```java
public List<Retrieved> retrieve(Long kbId, String query) {
    String expr = buildExpr(kbId);                      // ① 谁能搜哪些库
    if (expr == null) return List.of();                 // 没有可见库，直接返回空
    float[] vector = embeddingClient.embedOne(query);   // ② 问题向量化
    return vectorStore.search(vector, expr, props.getMilvus().getTopK()).stream()
            .filter(h -> h.score() >= props.getMilvus().getScoreThreshold())  // ③ 阈值过滤
            .map(h -> new Retrieved(h.sourceFilename(), h.chunkId(), h.docId(), h.content(), h.score()))
            .toList();
}
```

三个参数决定了检索质量，都在配置里：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `EMBEDDING_DIMENSION` | 1024 | 必须与 Milvus collection 维度一致 |
| `VECTOR_TOP_K` | 6 | 取回几条候选 |
| `VECTOR_SCORE_THRESHOLD` | 0.3 | 余弦相似度下限，低于它的片段丢弃 |

`buildExpr` 的分支逻辑（**权限落点**）：

```java
if (StpUtil.hasRole("ADMIN")) {
    if (kbId == null) return "id >= 0";              // 全量
    return "kb_id == " + kbId;                        // 指定库
}
// 普通用户：忽略传入的 kbId，只搜公开库
return "kb_id in [" + publicKbIds + "]";
```

### 重建的两条路

| 场景 | 入口 | 行为 |
| --- | --- | --- |
| 单个文档重新解析 | `POST /api/doc/{id}/reparse`（`doc:upload`） | `resetDoc` 清向量/切片 → 状态回 `UPLOADED` → 重新入队 |
| 整个知识库重建 | `POST /api/admin/vector/reindex/{kbId}`（`admin:vector:manage`） | 逐文档 `resetDoc` + 入队，返回文档数 |

两个方法都**没有 `@Transactional`**，这是刻意的：清理要先提交给数据库可见，否则异步线程可能读到
未提交的旧状态，导致切片重复插入。

### 删除是“不彻底”的

```java
vectorStore.deleteByDocId(doc.getId());
storageService.delete(doc.getObjectKey());
chunkMapper.deleteByDocId(doc.getId());
```

MySQL / Milvus / MinIO 三方没有分布式事务：可能向量删了但对象没删，或删到一半失败。
删库里用的 `@Transactional` 只覆盖 MySQL，回滚也恢复不了已经删掉的 MinIO 对象和向量。

## 四、改这里会牵连什么

| 改动 | 影响 |
| --- | --- |
| 改切片参数 | 只影响新文档；老文档要 `reparse` 才按新参数重切 |
| 改 `TextSplitter` 策略 | 所有新切片；建议同时 `reindex` 存量数据 |
| 增加解析格式 | 在 `DocumentParserFactory.parse` 的 `switch` 加分支 + 引入依赖 |
| 改 `VectorStore.VectorRecord` 字段（content/filename） | Milvus schema 变更，需要删 collection 重建（`ensureCollection` 只在不存在时创建） |
| 把 `raw_text` 去掉 | 降存储成本，但重解析必须回 MinIO 下载；且无法做全文审计 |
