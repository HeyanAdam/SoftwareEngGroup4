## 四、对 P1 的约定

1. **loginId 必须是用户主键**：`StpUtil.login(user.getId())`，不要用 username；否则 `StpInterfaceImpl` 查不到权限，全站 403。
2. **登录/当前用户接口请返回 `roles` + `permissions` 两个数组**（`AuthService.LoginResult` 已有该结构），P3 前端靠它做按钮显隐。
3. **`AuthService.resolveRegisterRole()` 现在找 `"ADMIN"`**：该角色码已不存在，实际效果是新注册用户一律是 `STUDENT`（符合接口文档 3.2「不允许首个注册用户自动成管理员」）。该段属 P2 任务 5，改动前会先与 P1 确认，不会单方面修改 `AuthService`。

---

## 五、对 P3 的约定

1. **按钮/菜单显隐用权限码判断**，不要按角色名硬编码（例如 `hasPerm('kb:view')`）。
2. **学生端只有 `chat:send`**：知识库、后台入口一律不显示（接口文档 11.5 禁止学生直接浏览知识库）。
3. **统一错误码处理**：
   - `401` + `10001` 未登录/过期 → 跳登录页
   - `403` + `10008` 无权限 → 提示无操作权限，不跳登录
   - `403` + `10009` 越权访问他人数据 → 提示无权访问
   - `429` + `10010` 限流；`423` + `10003` 账号锁定
4. 接口路径以接口文档 V1.1 为准：业务 `/api/v1/**`，后台 `/api/v1/admin/**`（该迁移属 P2 任务 7，尚未执行）。

### 7.3 合并时补的一处集成修正

P1 的 `AuthErrorCode` 新增了 `10011`（幂等键处理中）、`10012`（请求类型不支持）、`10013`（账号已禁用），而 P2 的 `common/ErrorCode` 的 `httpStatusOf()` 映射表不认识这三个码，会回落成 HTTP 400。已在 `ErrorCode.HTTP_STATUS` 补齐：

```
10011 → 409      10012 → 400      10013 → 403
```

> 说明：业务码仍以 P1 的 `AuthErrorCode` 为唯一口径，`ErrorCode` 只做取值一致的并行常量 + HTTP 映射，不另立标准。

### 7.4 两套异常处理器的分工（已确认不冲突）

| 处理器 | 作用范围 | 负责的错误 |
|---|---|---|
| `modules/auth/support/AuthExceptionHandler` | `@RestControllerAdvice(assignableTypes = AuthController.class)`，`@Order(HIGHEST_PRECEDENCE)` | 只有认证接口的 400 / 401 / 409 / 423 / 429、10011 / 10012 / 10013 |
| `common/GlobalExceptionHandler` | 全局兜底 | 其余接口的 `BizException`（10008 / 10009 等）、参数校验 400 / 10000、Sa-Token 401 / 403、兜底 500 / 90000 |

项目内 `StpInterface` 实现只有 `StpInterfaceImpl` 一个，无重复 Bean；初始化器顺序为 `RbacInitializer @Order(1)` → `AdminBootstrapInitializer @Order(2)`，不存在管理员重复创建。

### 7.6 与 P1 / P3 的边界（再次确认）

1. **认证接口的异常与错误码**由 P1 的 `AuthExceptionHandler` + `AuthErrorCode` 负责，P2 不重复定义。
2. **业务接口的鉴权与数据过滤**由 P1/P3 在各自 Controller 中调用：`@SaCheckPermission("权限码")` + `dataScopeService.requireSelf(userId)`，**禁止硬编码角色字符串**。
3. **接口路径前缀** `/api → /api/v1` 的迁移仍未执行（P2 任务 7），需独立分支改造后统一评审，本次不动。
4. 后续开发仍在各自 feature 分支进行，修复完成后 merge 回 `feat/auth-foundation` 做集成，不在集成分支写业务代码。
