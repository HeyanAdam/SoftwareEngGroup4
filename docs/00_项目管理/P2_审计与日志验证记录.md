# P2 审计与日志验证记录

> 归属：P2（RBAC 接口安全与集成）
> 验证时间：2026-11-19
> 关联文档：《P2交付说明_权限与认证契约.md》第 8.3 / 8.4 / 8.6 节

---

## 一、验证目标

1. 后台**写操作**是否真的落库到 `sys_audit_log`，字段是否完整（`action` / `resource_type` / `resource_id` / `request_id`）。
2. 每次请求是否都有可反查的 `request_id`，并且**响应头、服务端日志、审计表三处一致**。
3. 登录成功/失败是否有独立登录日志（`sys_login_log`）。
4. 审计写入失败是否会**影响主业务**（结论：不会，`AuditLogAspect` 只记录不阻断）。

## 四、实测记录

### 4.1 验收脚本自动断言（每次运行都验）

```
管理员改角色名（触发 @AuditLog）  code=0
审计记录新增                      条数 +1        （20 -> 21 / 16 -> 17 / 13 -> 14 均出现过）
审计内容                          UPDATE_ROLE | ROLE | 7 | 68d64f38d1d248059d1a0a607c53955c
```

- `action` = `UPDATE_ROLE`、`resource_type` = `ROLE`、`resource_id` = `7`（角色主键）、`request_id` 非空。
- 每跑一次脚本条数稳定 +1，说明**幂等**：脚本改回原角色名，但审计仍记录每次动作（审计就该如此）。

### 4.2 `request_id` 三处一致

| 位置 | 形态 |
|---|---|
| 响应头 | `X-Request-Id: 68d64f38d1d248059d1a0a607c53955c` |
| 服务端日志 | `2026-11-19 21:0x:xx.xxx INFO [http-nio-8080-exec-2] [68d64f38d1d248059d1a0a607c53955c] ...` |
| 审计表 | `sys_audit_log.request_id = 68d64f38d1d248059d1a0a607c53955c` |

复现方式（终端）：

```powershell
cd D:\SoftwareEngGroup4\deploy
docker compose exec mysql mysql -ukaoyan -pkaoyan123 kaoyan_ai -e "SELECT id,user_id,module,action,resource_type,resource_id,request_id,create_time FROM sys_audit_log ORDER BY id DESC LIMIT 5;"
```

然后到 IDEA 控制台搜同一个 `request_id`，能看到该请求的完整处理链日志。**答辩演示建议就用这一条**：先给审计行，再给日志行，讲"一个请求号串起三处"。

### 4.3 未登录/无权限是否留痕

- `401 + 10001`、`403 + 10008` 属于**鉴权失败**，不进 `sys_audit_log`（审计只记业务写操作），但在 INFO/WARN 日志里有 `requestId` 与失败原因。
- 登录成功/失败进 `sys_login_log`（由 P1 的 `AuthService` 调 `LoginLogService.record`）。本轮合并已把它从 auth 模块的重复实现切到 `modules.audit` 的单一实现，**不存在两套登录日志**。

### 4.4 审计失败不阻断业务

`AuditLogAspect` 采用 `try { 记录 } catch (Exception e) { log.warn }` 语义：审计写库异常只打 WARN，不向调用方抛错。验证方式：手动把 `sys_audit_log` 的写入搞失败（例如临时改坏表名）——业务接口仍返回 `code=0`，日志出现审计失败 WARN。**这条是为了保证"审计不该把后台改崩"**，答辩如被打断可这样说明。

## 五、日志格式与环境

`logback-spring.xml`：

```
%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] [%X{requestId:-no-req}] %logger{40} - %msg%n
```

- 无请求上下文时显示 `[no-req]`（启动期、定时任务），正常请求都带具体 requestId。
- 开发环境 `application-dev.yml` 把 `com.group4.kaoyan` 设成 DEBUG：可以看到 `OutboxMapper.resetStuck/selectPending` 的定时轮询日志持续滚动 —— 这是**正常现象**（`platform/messaging` 的出站消息补偿任务），不是启动没跑完。
- Flyway 启动日志 `Successfully validated 8 migrations` + `Current version of schema ... up to date` 说明库结构一致。

## 六、结论

| 检查项 | 结论 |
|---|---|
| 后台写操作留痕 | ✅ Admin 侧 9 个接口 + Knowledge/File 的写接口，验收断言条数 +1/次 |
| 审计字段完整性 | ✅ `action/resource_type/resource_id/request_id` 均非空 |
| 请求号贯穿 | ✅ 响应头 / 日志 / 审计表三处一致 |
| 登录日志单一实现 | ✅ 已收敛到 `modules.audit`，无重复 |
| 审计失败隔离 | ✅ 切面 `catch (Exception)` 只 `log.warn`，不影响业务返回（`AuditLogAspect:52-55`） |
| 遗留 | `before_json` 目前**全部为 null**：切面只写 `after_json`（`AuditLogAspect:49`），未做方法执行前快照。若答辩需要"改前/改后对比"，需在 `@Around` 的 `proceed()` 之前补一次查询快照（非本期要求，可作为后续增强点主动说明） |
