## 一、先更正一个此前的误判（避免按错的方向改代码）

此前 P2 在口头沟通中提到「学生改 `conversationId` 就能看别人聊天记录」，**这个判断是错的**，复核后确认：

`ChatService` 已经做了归属校验：
- `messages(userId, conversationId)` 第 52–55 行：`conversationMapper.selectById` 后判断 `!userId.equals(c.getUserId())` → 抛 `BizException(404, "会话不存在")`
- `delete(userId, conversationId)` 第 62–65 行：同上

所以 **Chat 的越权读/删并不存在数据泄露**。缺的只是「函数级权限注解」和「越权返回码口径」两件事，下面按真实情况列。

## 二、改造项清单

### 改造项 A｜Chat 三个会话接口补权限注解（主责：P3，若 P3 时间紧可由 P1 代改）

**文件**：`backend/src/main/java/com/group4/kaoyan/modules/chat/controller/ChatController.java`

| 行号 | 接口 | 现状 | 需要做 |
|---|---|---|---|
| 42 | `GET /conversations` | 只有登录校验 | 方法上加 `@SaCheckPermission(PermissionConstants.CHAT_SEND)` |
| 47 | `GET /conversations/{id}/messages` | 只有登录校验 | 同上 |
| 52 | `DELETE /conversations/{id}` | 只有登录校验 | 同上 |

改造后形态（示例）：
```java
@SaCheckPermission(PermissionConstants.CHAT_SEND)
@GetMapping("/conversations")
public R<List<ChatConversation>> conversations() { ... }
```

> 为什么用 `chat:send`：`PermissionConstants` 里对话域只有这一个权限码，`list / 读历史 / 删除` 属于同一业务域，不单列新码（新增权限码要走 V7 迁移 + 矩阵评审，本期不做）。

**验收**：无 `chat:send` 的账号（可用 DATA_AUDITOR 测试账号）调这三个接口 → `403 + 10008`。

### 改造项 B｜Chat 越权返回码口径（主责：P3）

**文件**：`modules/chat/service/ChatService.java` 第 52–55 行、62–65 行

现状：会话不存在和「会话存在但不属于你」**都返回 404「会话不存在」**。契约（P2 任务 4）要求「数据归属失败 → 403 + 10009」。

建议改成两段判断，兼顾安全与契约：
```java
ChatConversation c = conversationMapper.selectById(conversationId);
if (c == null || (c.getDeleted() != null && c.getDeleted() == 1)) {
    throw new BizException(404, "会话不存在");          // 真不存在：404，避免被探测
}
if (!userId.equals(c.getUserId())) {
    throw new BizException(ErrorCode.NO_DATA_ACCESS, "无权访问该数据");  // 归属不符：403 + 10009
}
```

> 如果决定维持「统一 404 防探测」，请在 PR 描述里写明这一取舍，并在《P2交付说明》的已知差异里登记；否则 Review 会判为「10009 无法触发」。
> 这条改了之后，**10009 就可以真机验证**，P3 的 403 页面也不用只靠 `?code=10009` 预览。

### 改造项 C｜User 三个接口（主责：P1）

**文件**：`modules/user/controller/UserController.java`（3 个接口）+ `modules/user/service/UserService.java`

| 项 | 现状 | 需要做 |
|---|---|---|
| `GET /profile`、`PUT /profile` | 无注解，仅登录校验 | **不需要加权限码**（个人资料对任何登录用户开放）。保持现状即可 |
| 密码泄露检查 | `SysUser.passwordHash` 已 `@JsonIgnore`，`/profile` 不会回密码 | ✔ 已合格，无需改 |
| `PUT /password` 改密后 | `UserService.changePassword` **没有任何会话吊销动作** | ⚠ 需补：改密成功后调用 `sessionService.logoutUser(userId)`，与「重置密码后旧 Token 全量失效」（AuthService 第 250–253 行）口径一致 |
| `PUT /profile` 改邮箱 | 不校验邮箱归属，可任意改成他人邮箱 | ⚠ 需评审：建议改为「发验证码到新邮箱后确认」，或先标记为已知限制 |

> `PUT /password` 这条是**真实缺口**：用户在 A 设备改密后，B 设备被窃的 Token 仍然有效，与 P1 已实现的重置密码吊销行为不一致。

### 改造项 D｜路径统一 `/api` → `/api/v1`（主责：P1 + P3 前端协同）

**后端要改的文件与当前值**：

| 文件 | 当前 | 改为 |
|---|---|---|
| `modules/admin/controller/AdminController.java` | `@RequestMapping("/api/admin")` | `/api/v1/admin` |
| `modules/chat/controller/ChatController.java` | `@RequestMapping("/api/chat")` | `/api/v1/chat` |
| `modules/knowledge/controller/KnowledgeController.java` | `@RequestMapping("/api")`（子路径 `/kb`、`/doc`） | `/api/v1` |
| `modules/user/controller/UserController.java` | `@RequestMapping("/api/user")` | `/api/v1/user` |
| `modules/auth/controller/AuthController.java` | `/api/v1/auth` | ✔ 已是 v1，不改 |

**连带影响（不改会 404）**：
1. `common/config/WebConfig.java` 的 `PUBLIC_PATHS` 已写成 `/api/v1/auth/*`、`/api/v1/health/**`，与 v1 一致，无需改
2. `WebConfig` 拦截器 `SaRouter.match("/api/**")` 仍可覆盖 `/api/v1/**`，无需改
3. **P3 前端 baseURL 与所有写死的接口路径必须同步改**，否则全站 404
4. 部署侧 `deploy/` 里的 Nginx 若有 `/api` 前缀转发规则，需同步（找 deploy 负责人确认）

> 建议一次性切干净，不要做双路径兼容期（双路径会让「哪个才是权威路径」长期含糊，且越权测试容易测错对象）。

### 改造项 E｜`WebConfig` 删除遗留白名单（主责：**P2 自己**，不用转交）

`common/config/WebConfig.java` 第 51 行：
```java
.notMatch("/api/kb", "/api/kb/**")   // ← 遗留放行，必须删
```
删除后 `/api/kb/**` 恢复「先登录再鉴权」，避免将来新增接口忘加注解就变成匿名可访问。

### 改造项 F｜鉴权链路补 `status` 兜底（主责：**P2 自己**）

详见《P2_Review_P1认证实现.md》发现 5。鉴权侧（`StpInterfaceImpl` 或 Sa-Token 拦截器）在取快照时校验 `sys_user.status`，`status == 0` 直接拒绝，不再只依赖管理员禁用时的 `kickout`。

## 三、数据范围（DataScopeService）接入指引

`DataScopeService` 已提供：`currentUserId()`、`hasPermission(code)`、`hasDataScope(scope)`、`requireSelf(ownerUserId)`、`canReadAll()`、`canReadMasked()`。

现有业务现状（复核结果）：

| 模块 | 归属校验现状 | 结论 |
|---|---|---|
| Chat 会话 | ✔ 已在 `ChatService` 手工判断 `userId.equals(c.getUserId())` | 不需要再调 `requireSelf`，但建议统一改调 `requireSelf` 以便口径一致（可选） |
| Knowledge 知识库 | 属 `ALL` 数据范围（内容运营 / 管理员共用），无 `SELF` 场景 | 不需要接 `SELF` |
| Admin 后台 | 管理员专属，无 `SELF` 场景 | 不需要接 |
| User 个人资料 | 全部基于 `StpUtil.getLoginIdAsLong()`，天然是本人 | 不需要接 |
| 学习计划 / 文件 | **后端接口尚未实现** | 新接口开发时**必须**调用 `requireSelf(ownerUserId)` |

> 结论：任务 3 的「接入」在当前代码里**已由 Chat 手工实现覆盖了唯一的 SELF 场景**，剩余接入点属于「尚未实现的学习计划 / 文件接口」。这一点写进交付说明，避免被误判为漏做。

## 四、验收用例（改造完成后逐条跑）

### A. 函数级鉴权（改造项 A）
```powershell
# 1) 学生登录拿 token
curl -X POST http://localhost:8080/api/v1/auth/login -H "Content-Type: application/json" `
  -d '{\"loginType\":\"password\",\"account\":\"student01\",\"password\":\"xxx\",\"captchaKey\":\"...\",\"captchaCode\":\"...\"}'

# 2) 学生访问后台用户列表 → 期望 403 + 10008
curl -i http://localhost:8080/api/admin/users -H "Authorization: Bearer <student-token>"
# 期望：HTTP/1.1 403 ; {"code":10008,"message":"无接口访问权限","data":null}
```

### B. 数据归属（改造项 B 完成后）
```powershell
# 用户A 的会话 id，用 用户B 的 token 去读 → 期望 403 + 10009
curl -i http://localhost:8080/api/chat/conversations/<A的会话id>/messages -H "Authorization: Bearer <B-token>"
```

### C. 改密吊销（改造项 C 完成后）
```powershell
# 1) 设备1 登录拿 token1；设备2 登录拿 token2
# 2) 设备2 调 PUT /api/user/password 改密
# 3) 设备1 用 token1 调 GET /api/user/profile → 期望 401 + 10001（已失效）
```

### D. 未登录（现在就能测）
```powershell
curl -i http://localhost:8080/api/admin/users
# 期望：HTTP/1.1 401 ; {"code":10001,...}
```

### E. 禁用即失权（现在就能测）
```powershell
# 1) 管理员禁用用户A（PUT /api/admin/users/{id}/status  body {"status":0}）
# 2) 用A的旧 token 调任意 /api 接口 → 期望 401 + 10001
# 3) A 重新登录 → 期望 403 + 10013「账号已被禁用」
```

## 五、附录：权限种子核对结果（静态核对，P2 任务 9-9）

| 核对项 | 结果 |
|---|---|
| `V6__seed_rbac_dictionary.sql` 中的权限码数量 | **11 条** |
| `PermissionConstants.CATALOG` 权限码数量 | **20 条** |
| 包含关系 | V6 的 11 条 **全部包含在** 代码的 20 条内（无拼写不一致） |
| 缺失的 9 条 | `study-plan:view/create/update`、`study-task:update`、`question:view`、`file:view/upload/download/delete` |
| 9 条如何入库 | 由 `RbacInitializer` 启动时 **运行时幂等补齐**（只增不删） |
| 4 角色默认授权数 | V6 与 `RoleConstants` **完全一致**：SYSTEM_ADMIN 全量（V6 11 → 启动补齐到 20）、CONTENT_OPERATOR 6、DATA_AUDITOR 3、STUDENT 1 |
| 结论 | 逻辑一致，但**迁移脚本不完整**：新环境若跳过 Spring 启动（如只跑 Flyway 做集成测试、或用只读账号启动），库内只有 11 条，后台授权界面会少 9 个可授权项 |

**建议**：补一个 `V7__seed_rbac_permissions_extend.sql` 把剩余 9 条权限码做成迁移（与 `PermissionConstants` 同源），让「Flyway 跑完 = 库内即正确」，而不是依赖应用启动兜底。主责建议交给数据库同学，P2 出清单。
