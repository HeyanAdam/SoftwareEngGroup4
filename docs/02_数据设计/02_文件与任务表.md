# 文件与任务表（V4 / V5）

对应迁移脚本：

- `backend/src/main/resources/db/migration/V4__file_storage.sql`
- `backend/src/main/resources/db/migration/V5__async_task_and_outbox.sql`

对应接口文档：`考研AI导学系统接口设计文档_V1.1适配版.docx` 第 10 章（文件存储）、11.3-11.4（知识文档）、6.3（图片搜题任务）、2.6（文件与存储错误码 30001-30009）。

## 1. 概述与表关系

```text
file_object  1 ──── N  file_upload_session  1 ──── N  file_upload_part
      │                        （合并成功后生成 file_object）
      │
      └── scene = KNOWLEDGE_DOCUMENT 时，与已有 kb_document 对应同一份原件

sys_async_task  1 ──── N  sys_message_outbox  1 ──── N  sys_message_consume_log
     （业务事务内同写）            （发送成功/重试）          （消费侧幂等）
```

| 表 | 用途 | 写入模块 |
|---|---|---|
| `file_object` | 头像、题目图片、学习资料、知识文档原件的元数据；只存对象键，不存二进制 | `modules/file` |
| `file_upload_session` | 大文件分片上传会话，支撑初始化、断点续传、合并、取消 | `modules/file` |
| `file_upload_part` | 单个分片的落盘记录 | `modules/file` |
| `sys_async_task` | 文档解析、切片、Embedding、图片搜题、AI 报告等异步任务 | `modules/knowledge`、`modules/chat`、`platform/messaging` |
| `sys_message_outbox` | 业务落库后可靠投递 MQ 消息（Outbox 模式） | 各业务模块（与业务事务同提交） |
| `sys_message_consume_log` | 消费端幂等记录，防重复处理 | `platform/messaging` |

数据归属：`file_object.owner_user_id`、`file_upload_session.user_id` 一律取登录态用户，不接受前端传入；`sys_async_task.user_id` 可为空（系统任务）。

## 2. file_object（文件对象元数据）

### 2.1 字段

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 是 | 自增 | 主键，接口中的 `file_id` |
| `owner_user_id` | BIGINT | 是 | — | 归属用户，来自登录态 |
| `scene` | VARCHAR(32) | 是 | — | `AVATAR`/`QUESTION_IMAGE`/`STUDY_MATERIAL`/`KNOWLEDGE_DOCUMENT`/`CHAT_ATTACHMENT` |
| `bucket_name` | VARCHAR(64) | 是 | — | MinIO 桶名，默认 `kaoyan-files` |
| `object_key` | VARCHAR(512) | 是 | — | 对象键，不含桶名 |
| `original_filename` | VARCHAR(255) | 是 | — | 原始文件名 |
| `file_ext` | VARCHAR(16) | 否 | NULL | 扩展名，小写不带点 |
| `content_type` | VARCHAR(128) | 是 | — | MIME 类型，下载时回填响应头 |
| `file_size` | BIGINT | 是 | — | 文件字节数 |
| `sha256` | CHAR(64) | 否 | NULL | SHA-256 十六进制；下载 `ETag` 与秒传使用 |
| `status` | VARCHAR(32) | 是 | `READY` | `READY` 可用 / `FAILED` 写入或校验失败 |
| `deleted` | TINYINT | 是 | 0 | 逻辑删除：0 否，1 是 |
| `create_time` | DATETIME | 是 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 是 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |

### 2.2 主键与唯一键

- 主键：`id`
- 唯一键：`uk_file_object_key (bucket_name, object_key)` —— 同一桶内对象键唯一，重复合并写同一对象时不会产生两条元数据

### 2.3 索引及对应查询

| 索引 | 支撑查询 |
|---|---|
| `idx_file_owner (owner_user_id)` | `GET /api/v1/files` 列表：`owner_user_id = ? AND deleted = 0` |
| `idx_file_hash (owner_user_id, sha256)` | 秒传/去重：同一用户相同哈希是否已有可用文件 |
| `idx_file_scene_status (scene, status)` | 按场景与状态筛选（如题目图片清理、知识文档原件统计） |

### 2.4 状态与生命周期

```text
写入（批量上传 / 分片合并成功） -> READY
写入或校验失败                -> FAILED
删除文件                      -> deleted = 1（对象另行从 MinIO 删除）
```

- 数据库只保存对象键，不保存文件二进制。
- 删除优先逻辑删除，物理清理由运维或定时任务处理。
- 哈希可为空；一旦计算则保持不变，作为 `ETag` 的稳定来源。

### 2.5 对应接口

| 接口 | 使用方式 |
|---|---|
| `POST /api/v1/files/batch` | 每个文件插入一条，返回 `file_id`、`original_filename`、`file_size`、`content_type`、`status` |
| `GET /api/v1/files` | 按 `owner_user_id`、`scene`、`status`、`deleted` 分页查询 |
| `GET /api/v1/files/{file_id}/content` | 取 `bucket_name`/`object_key`/`content_type`/`file_size`/`sha256`，支持 Range 与 206 响应 |
| `DELETE /api/v1/files/{file_id}` | `deleted = 1` |
| `POST /api/v1/knowledge-bases/{kb_id}/documents` | `scene = KNOWLEDGE_DOCUMENT`，与 `kb_document.object_key` 对应 |

错误码：30001 文件不存在、30008 无权访问、30009 下载范围不合法（416）。

## 3. file_upload_session（大文件上传会话）

### 3.1 字段

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 是 | 自增 | 主键，接口中的 `session_id` |
| `user_id` | BIGINT | 是 | — | 上传用户 |
| `original_filename` | VARCHAR(255) | 是 | — | 原始文件名 |
| `file_size` | BIGINT | 是 | — | 文件总字节数 |
| `content_type` | VARCHAR(128) | 是 | — | MIME 类型 |
| `file_hash` | CHAR(64) | 否 | NULL | 整文件 SHA-256，完成时校验，支持秒传 |
| `part_size` | INT | 是 | — | 分片大小（字节），默认 5MB |
| `part_count` | INT | 是 | — | 分片总数，由 `file_size` 与 `part_size` 计算 |
| `uploaded_count` | INT | 是 | 0 | 已上传分片数 |
| `bucket_name` | VARCHAR(64) | 是 | — | MinIO 桶名 |
| `object_key` | VARCHAR(512) | 否 | NULL | 合并后的正式对象键，完成前为空 |
| `status` | VARCHAR(32) | 是 | `INIT` | `INIT`/`UPLOADING`/`MERGING`/`COMPLETED`/`FAILED`/`CANCELLED` |
| `expires_at` | DATETIME | 否 | NULL | 会话过期时间，过期后可清理分片 |
| `create_time` | DATETIME | 是 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 是 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |

### 3.2 主键与索引

- 主键：`id`
- `idx_upload_user_status (user_id, status)`：用户的上传中会话、重复初始化复用判断
- `idx_upload_expire (status, expires_at)`：过期会话清理
- `idx_upload_hash (user_id, file_hash)`：同一用户相同文件复用会话或直接秒传

### 3.3 状态机

```text
INIT -> UPLOADING -> MERGING -> COMPLETED
                  -> FAILED
                  -> CANCELLED
```

- 只有 `COMPLETED` 才允许生成正式 `file_object`。
- 完成前 `object_key` 允许为空。
- 取消（`DELETE /files/upload-sessions/{session_id}`）置 `CANCELLED`，分片另行清理。
- 过期通过 `status` 与 `expires_at` 判定。

### 3.4 对应接口

| 接口 | 使用方式 |
|---|---|
| `POST /api/v1/files/upload-sessions` | 插入会话，计算 `part_count`，返回 `session_id`/`part_size`/`part_count`/`uploaded_parts`/`expires_at` |
| `GET /api/v1/files/upload-sessions/{session_id}` | 读会话 + 分片表，返回已上传分片序号 |
| `POST /api/v1/files/upload-sessions/{session_id}/complete` | 校验分片完整性与哈希，置 `MERGING` 后合并，成功置 `COMPLETED` |
| `DELETE /api/v1/files/upload-sessions/{session_id}` | 置 `CANCELLED` |

错误码：30004 上传会话不存在、30005 分片不完整、30006 合并失败、30007 哈希校验失败。

## 4. file_upload_part（上传分片）

### 4.1 字段

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 是 | 自增 | 主键 |
| `session_id` | BIGINT | 是 | — | 所属上传会话 |
| `part_number` | INT | 是 | — | 分片序号，从 1 开始 |
| `part_size` | INT | 是 | — | 分片字节数（最后一个分片可小于 `part_size`） |
| `part_hash` | CHAR(64) | 否 | NULL | 分片 SHA-256，来自请求头 `X-Part-Hash` |
| `bucket_name` | VARCHAR(64) | 是 | — | 分片所在桶 |
| `object_key` | VARCHAR(512) | 是 | — | 分片对象键 |
| `status` | VARCHAR(32) | 是 | `UPLOADED` | `UPLOADED` 已落盘 / `FAILED` 校验失败 |
| `create_time` | DATETIME | 是 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 是 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |

### 4.2 主键与唯一键

- 主键：`id`
- 唯一键：`uk_upload_part (session_id, part_number)` —— 同一会话同一序号只保留一条当前记录
- `idx_upload_part_session_status (session_id, status)`：查询已上传分片、统计 `uploaded_count`

### 4.3 状态与规则

```text
上传成功 -> UPLOADED
校验失败 -> FAILED（允许前端重传覆盖同一 part_number）
```

- `part_number` 从 1 开始，最大为 `part_count`。
- 每次成功写入后累加会话 `uploaded_count`（同一序号重传不重复计数）。
- 合并前确认 `uploaded_count = part_count`。
- 合并成功后才生成正式 `file_object`。

### 4.4 对应接口

`PUT /api/v1/files/upload-sessions/{session_id}/parts/{part_number}`：`Content-Type: application/octet-stream`，请求头 `X-Part-Hash`，分片大小取自请求体长度。

## 5. sys_async_task（异步任务）

### 5.1 字段

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 是 | 自增 | 主键，对外即 `task_id` |
| `task_no` | VARCHAR(64) | 是 | — | 业务唯一任务号，内部排查与 MQ 关联 |
| `task_type` | VARCHAR(32) | 是 | — | `DOC_PARSE`/`DOC_CHUNK`/`EMBEDDING`/`IMAGE_QUESTION`/`AI_REPORT` |
| `biz_type` | VARCHAR(32) | 是 | — | `DOCUMENT`/`QUESTION`/`KNOWLEDGE_BASE` 等 |
| `biz_id` | BIGINT | 否 | NULL | 业务对象主键，如 `document_id` |
| `user_id` | BIGINT | 否 | NULL | 发起用户，系统任务可为空 |
| `status` | VARCHAR(32) | 是 | `PENDING` | `PENDING`/`RUNNING`/`RETRY_WAIT`/`SUCCEEDED`/`FAILED`/`CANCELLED` |
| `progress` | INT | 是 | 0 | 进度 0-100 |
| `retry_count` | INT | 是 | 0 | 已重试次数 |
| `payload_json` | JSON | 否 | NULL | 任务入参，如图片任务 `extra_question` |
| `result_json` | JSON | 否 | NULL | 任务结果，图片任务含识别结果与 `result_path` |
| `error_message` | VARCHAR(1000) | 否 | NULL | 失败原因 |
| `next_retry_at` | DATETIME | 否 | NULL | 下次重试时间 |
| `create_time` | DATETIME | 是 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 是 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |
| `finished_time` | DATETIME | 否 | NULL | 进入终态的时间 |

### 5.2 主键与索引

- 主键：`id`
- 唯一键：`uk_async_task_no (task_no)`
- `idx_async_task_status (status, next_retry_at)`：调度器扫描待执行/待重试任务
- `idx_async_task_biz (biz_type, biz_id)`：按业务对象查任务历史
- `idx_async_task_user (user_id)`：用户任务列表

### 5.3 状态机与对外映射

```text
PENDING -> RUNNING -> SUCCEEDED
                   -> RETRY_WAIT -> RUNNING
                   -> FAILED
PENDING/RUNNING    -> CANCELLED

接口对外：
PENDING  -> QUEUED
RUNNING  -> PROCESSING
SUCCEEDED-> SUCCEEDED
FAILED   -> FAILED
RETRY_WAIT / CANCELLED 不对外暴露
```

- `progress` 范围 0-100，终态应置 100 或保持最后进度。
- 失败任务保留 `error_message`；重试依赖 `retry_count` 与 `next_retry_at`。
- 终态写 `finished_time`。
- 同一业务对象不得无限制生成重复活动任务，由服务层在 `PENDING`/`RUNNING`/`RETRY_WAIT` 状态下做幂等判断（表结构不做部分唯一约束）。

### 5.4 对应接口

| 接口 | 使用方式 |
|---|---|
| `POST /api/v1/knowledge-bases/{kb_id}/documents` | 创建 `task_type=DOC_PARSE`、`biz_type=DOCUMENT`、`biz_id=document_id`，返回 `task_id` |
| `POST /api/v1/image-question-tasks` | 创建 `task_type=IMAGE_QUESTION`、`biz_type=QUESTION`，返回 `task_id`、`status=QUEUED`、`result_path` |
| `GET /api/v1/image-question-tasks/{task_id}` | 读状态与 `result_json` |
| `GET /api/v1/knowledge-documents/{document_id}` | 文档状态来自 `kb_document.status`，任务状态来自本表 |

文档处理状态（`kb_document.status`，仅作说明）：`UPLOADED -> PARSING -> SPLITTING -> EMBEDDING -> READY / FAILED`。

## 6. sys_message_outbox（消息发送 Outbox）

### 6.1 字段

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 是 | 自增 | 主键 |
| `event_id` | VARCHAR(64) | 是 | — | 消息唯一事件 ID，消费端据其幂等 |
| `exchange_name` | VARCHAR(128) | 是 | — | 交换机，如 `kaoyan.direct` |
| `routing_key` | VARCHAR(128) | 是 | — | 路由键，如 `doc.parse.task` |
| `message_type` | VARCHAR(64) | 是 | — | 消息类型，如 `DOC_PARSE_TASK` |
| `biz_key` | VARCHAR(128) | 否 | NULL | 业务键，便于排查 |
| `payload_json` | JSON | 是 | — | 消息体 |
| `status` | VARCHAR(32) | 是 | `PENDING` | `PENDING`/`PUBLISHED`/`RETRY_WAIT`/`FAILED` |
| `retry_count` | INT | 是 | 0 | 已重试次数 |
| `next_retry_at` | DATETIME | 否 | NULL | 下次重试时间 |
| `last_error` | VARCHAR(1000) | 否 | NULL | 最近一次发送错误 |
| `published_at` | DATETIME | 否 | NULL | 发送成功时间 |
| `create_time` | DATETIME | 是 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 是 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |

### 6.2 主键与索引

- 主键：`id`
- 唯一键：`uk_outbox_event (event_id)`
- `idx_outbox_pending (status, next_retry_at)`：投递器扫描待发送/待重试消息
- `idx_outbox_biz (message_type, biz_key)`：按业务排查消息

### 6.3 状态机

```text
PENDING -> PUBLISHED
        -> RETRY_WAIT -> PENDING
        -> FAILED
```

- 业务表写入与 Outbox 插入必须在同一数据库事务中。
- 发送成功置 `PUBLISHED` 并写 `published_at`；失败写 `last_error` 与 `next_retry_at`。
- 交换机与路由键沿用现有 `RabbitTopologyConfig`：`kaoyan.direct`、`doc.parse.task`、队列 `doc_parse_queue`。

## 7. sys_message_consume_log（消费幂等记录）

### 7.1 字段

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 是 | 自增 | 主键 |
| `message_id` | VARCHAR(64) | 是 | — | 消息 ID，对应 `sys_message_outbox.event_id` |
| `consumer_name` | VARCHAR(128) | 是 | — | 消费者标识 |
| `biz_key` | VARCHAR(128) | 否 | NULL | 业务键 |
| `status` | VARCHAR(32) | 是 | `PROCESSING` | `PROCESSING`/`SUCCEEDED`/`FAILED`/`DEAD_LETTER` |
| `retry_count` | INT | 是 | 0 | 消费重试次数 |
| `error_message` | VARCHAR(1000) | 否 | NULL | 失败原因 |
| `create_time` | DATETIME | 是 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 是 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |

### 7.2 主键与索引

- 主键：`id`
- 唯一键：`uk_consume_message (message_id, consumer_name)`：同一消费者对同一消息只处理一次
- `idx_consume_status (status, update_time)`：扫描长时间 `PROCESSING`、统计失败与死信
- `idx_consume_biz (biz_key)`：按业务排查

### 7.3 状态机

```text
PROCESSING -> SUCCEEDED
           -> FAILED
           -> DEAD_LETTER（超过重试次数）
```

- 重复消息先查本表，命中 `SUCCEEDED` 直接 ACK 丢弃。
- RabbitMQ ACK 只能在业务成功且消费记录更新之后执行。

## 8. 迁移与跨组约定

### 8.1 版本归属

| 版本 | 内容 | 负责人 |
|---|---|---|
| V1 | 原有 10 张表基线 | A |
| V2 | `user_profile`、`user_study_goal` | A |
| V3 | `sys_idempotency_record`、`sys_login_log`、`sys_audit_log` | A |
| V4 | `file_object`、`file_upload_session`、`file_upload_part` | B |
| V5 | `sys_async_task`、`sys_message_outbox`、`sys_message_consume_log` | B |

已合并的迁移禁止修改；需要变更时新增更高版本。

### 8.2 跨组约定

- 主键：`BIGINT` 自增；对外字段 `file_id`/`session_id`/`task_id` 即主键 `id`。
- 表名小写下划线；时间统一 `DATETIME`；文件大小 `BIGINT`。
- 文件哈希 SHA-256，十六进制大写或小写需全项目统一（建议小写），长度固定 64。
- 分片序号从 1 开始；分片默认大小 5MB（`5242880`）。
- 文件二进制只存 MinIO，MySQL 只存元数据与对象键。
- 逻辑删除使用 `deleted` 字段，不物理删除业务数据。
